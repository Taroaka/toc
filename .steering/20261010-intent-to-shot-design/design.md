# 意図を残して、見せ方を選べる制作フロー

**提案段階。現在のruntime schemaではない。赤ペン回答で範囲を決めてから実装する。**

## 1. 制作の中心を「誰を描くか」から「何をどう見せるか」へ

最初にscene全体と前後のcut、原作上の事実・知識・開示順、採用済み音声を読む。作者は視聴者に届けたいものを考え、必要な人物の目的・感情・関係を踏まえ、行為と画の選び方を決める。その**選んだ意図と具体的な指示**をJSONに残す。思考過程の逐語記録や全項目の心理分析は要求しない。

例えば「もっとこちらを向いてほしい」は相手への目的であり、「嬉しい」は感情である。目的をもつ人物が相手の視線を探し、手を差し出し、反応を待つという演技を作者が選べる。ただし感情ラベルから定型の身振りを自動挿入しない。顔が見えない画では表情に頼らず、映る身体・距離・動きや画面外の音で伝える選択をする。

起承転結、導入の全景、全員の反応、毎回の画角変更は義務にしない。既に位置関係が分かっていれば寄りから始めてもよい。反復・静止・見せないことも演出として成立させる。

## 2. 一本の共通経路

```text
原作・sceneの意図・前後のcut・人物/衣装の状態・採用音声
    ↓ 作者がscene単位で撮り方と演技を選ぶ
cutの意図 + 時間内のshot計画（JSON）
    ↓ 型/ID/世界の状態/音声区間を検証
選択モデルで実行可能な入力方式と参照の割当てを確認
    ↓ 必要な素材・開始画・任意の終了画を解決/作成
画像request / 動画requestを同じ計画から別々に構築
    ↓ 実prompt・参照bytes/hash・duration・モデルを固定
API生成 → 既存ナレーションの時間軸に編集 → 試聴/訂正
```

フロント、CLI、Codex会話はこの同じ共通処理を入口にする。スキルにも同じartifactを読む手順を記載し、チャットの自由記述promptを別の正本にしない。ユーザー訂正は安定したcut/shot IDへ適用してversionと依存関係を更新する。

生成能力の確認は画像生成前と送信直前に行う。後から映る人物の参照経路がないまま開始画像だけ先に有料生成することを避ける。品質を採点するcritic段階は追加しない。

## 3. 独立させる情報

| 情報 | 保持するもの | 避ける結び付き |
|---|---|---|
| 物語上の事実 | 原作の出来事、所在、衣装・所持物、変化、知識・開示範囲 | カメラに映らない＝存在しない |
| cutの参加者 | cut内で作用する人物・物と安定ID。複数人assetならmember ID | 全参加者＝開始画で描く全員 |
| その瞬間の画 | visible subjects、身体部分、向き、遮蔽、attention、構図 | 人物がいる＝顔/全身を見せる |
| 演技 | actor/target、目的、必要なら感情、きっかけ、観察可能な行為・反応 | 感情＝定型gesture、全員同時に動く |
| 撮影 | 画の大きさ・位置・焦点・移動と、それを選んだ短い理由 | カメラ移動＝人物の移動、寄り＝必ず顔 |
| 実参照 | identity、衣装/状態、場所、構図、開始/終了の用途と送信先 | assetを登録した＝APIへ渡った、参照画像にいる＝画面に出す |

人物が最初は画面外、カメラで見える、歩いて入る、焦点だけが合う、変身して別状態になる、を別の出来事として扱う。必須の開示eventは原作の許可と照合する。既に世界にいる人物が画角に入るだけなら、新人物の創作と同一視しない。

動作の物理的な前提と、映像で見せる必要のある証拠も分ける。手が空いている、靴を脱いでいる、相手がそばにいる等の前提を保っても、その全てを開始画に映す必要はない。必要な行為の証拠は、cut/sceneのどの時点・どのshotで伝えるかを割り当てる。`must_show`を開始画像へ一括展開しない。意図的に見せない原因から反応を先に映す構成も、原作の情報開示に反しなければ選べる。

## 4. JSONの形（概念。キー名の確定は実装時）

既存の`character_ids`を黙って別の意味に変えず、新しいversionにする。以下は足元の撮り方を説明する抽象例で、作品データや新しい物語の生成ではない。文字列のrefは既存artifactのIDへ解決する。

```json
{
  "schema_version": "cut_direction_v2_proposal",
  "cut_id": "cut_a",
  "source_beat_ids": ["beat_a"],
  "intent": "表情で受け取った気持ちを、立ち去る足取りへつなぐ",
  "narration_binding": {"adopted_audio_ref": "audio_a", "range_ref": "range_a"},
  "participants": [{"entity_id": "person_a", "member_id": null}],
  "world_state": {"start_ref": "state_a", "end_ref": "state_b"},
  "shots": [{
    "shot_id": "shot_a",
    "range_ref": "range_a",
    "intent": "足取りを見せて退出を伝える",
    "initial_view": {
      "subjects": [{
        "entity_id": "person_a", "member_id": null,
        "visible_parts": ["feet", "garment_hem"],
        "view_description": "足元のみ。上半身は画角の外",
        "state_ref": "wardrobe_a"
      }],
      "attention": "足取りと床への接触",
      "composition": "床に近い高さで足元を切り取る"
    },
    "performance": [{
      "actor_id": "person_a", "target_id": null,
      "objective": "その場を立ち去る", "emotion": null,
      "basis": "source_action", "source_refs": ["beat_a"],
      "behavior": "既存の歩行を続け、画角の外へ抜ける"
    }],
    "camera": {
      "framing": "足元の寄り", "movement": {"kind": "locked_off", "description": "固定"},
      "focus": {"target": "足元と床の接触部", "change": null},
      "lens_mm": null
    },
    "presentation_events": [{
      "event_id": "ev_a", "kind": "frame_exit", "entity_ids": ["person_a"],
      "trigger": "歩行が画角の端に達する", "timing_ref": null,
      "world_change_ref": null
    }],
    "end_view": null,
    "reference_requirements": [
      {"entity_id": "person_a", "state_ref": "wardrobe_a", "usage": "initial_image_identity"}
    ]
  }]
}
```

足元を見せるために新しい人物assetを作らず、同じ人物・衣装stateの見える部分だけを使う。複数人assetを参照するときは実体数とmemberを識別し、同一画像から同じ人物を複製しない。変身前後のstate variantと同一shot内のresult frameの既存基盤は再利用する。

`performance`は必要な役だけ。`basis`はsource_action / user_direction / directorial_interpretation等で、演出解釈を原作の心理事実へ昇格させない。人物がいない画は`subjects: []`、`performance: []`でよい。手や足がある画は人物ありとして扱い、主/補助という編集上の役割とは切り離す。

## 5. null、空配列、欠落、未解決

| 表現 | 意味 | 例 |
|---|---|---|
| 値 | 選択した具体的な指定 | framing=足元、movement=locked_off |
| `null` | その項目を意図的に指定しない/適用しない。項目別に一意に定義 | lens_mm=nullは焦点距離の数値を指定しない。target_id=nullは相手のない行為 |
| `[]` | その一覧に項目がない | subjects=[]は画に人物/物の個別対象を列挙しない。場所・光・構図は別に保持 |
| 欠落 | authoring入力では任意項目の省略。正規化で既定を適用 | 作品の撮影方針を継承する項目はその規則を使う |
| unresolved | 実行に要るID・参照・時間が未解決。nullで代用しない | 登場する人物の衣装asset未解決ならrequestを作らない |

実行用JSONでは所定のキーを揃える。継承元・値の由来を保存し、継承解除のnullを空値fallbackで復活させない。既存film overrideのnull=clearは維持する。`end_view:null`は終了画の特別な構図指定をしない意味であり、世界の終了状態を不明にする意味ではない。`focus.change:null`も「カメラ固定」を意味しない。カメラ固定には明示値を使う。

作品のJSONをそのまま外部APIへ投げない。変換処理がAPIのschemaに合わせ、任意引数を省略し、必須引数の型と値を保証する。source ID、採用音声、実行時間、送信に必要な画像・hash・モデル等はnull不可。撮影に不要な心理・レンズ・焦点移動はnullableにする。

## 6. 撮影を考える単位と音声

scene作者が隣接cutを同時に扱い、寄り引き・向き・注視点・動き・間の関係を選ぶ。視線方向、進行方向、身体の向き、光・衣装の継続を保ち、変える必要があれば理由を残す。180度等の撮影文法を絶対validatorにしない。未執筆の次sceneは上流の意図/状態として読む。存在しない次のshot情報は推測で埋めない。

採用済みナレーションがある場合は既存の音声区間を時間軸の正本とする。音声のhash、開始/終了、無音、scene内offsetを保持し、映像のみ更新する経路を用意する。通常のp400再投影で原稿や音声requestを上書きしない。

**赤ペンQ1**: ひとつの既存cut/音声区間に、必要なら複数shotを割り当てる案を推奨する。各shotは通常1つの連続撮影とし、寄り引きの編集はshot境界で行う。区間の総尺と音声は変えない。新規設計は1 beat=1 cutを強制しない既存方針を継続する。

長尺のため同じshotを複数API clipで作ることと、編集で画を切り替えることは別。モデルの最小/最大尺は実送信側で解決し、余剰はtrimと編集で処理する。分割数と料金見積りを表示する。通常速度で行為が収まらないなら、無断の音声短縮/速度変更ではなく、映像構成の訂正候補を返す。

## 7. 画像と動画へ違う情報を渡す

### 開始画像

その瞬間のsubjects、見える身体部分、姿勢、構図、必要な衣装/state参照のみから描画指示を組む。全参加者・将来の反応・終了状態は開始画の肯定的被写体リストに展開しない。画面外の人物は世界の状態に残す。identity用の全身参照画像を渡しても、描く範囲はshotの足元/背中等を優先する。場所が世界に存在しても、背景の全景を必ず描かせない。

### 動画

開始画像に、actor/targetに結び付いた順序付き行為・反応、カメラ移動、焦点、登場/退出、必要な状態変化、終了時に続ける動作を加える。衣装や個体数の維持と、身体を静止させる命令を分離する。「手渡して受け取った後に喜ぶ」はひとつの行為の因果なので、主動作1つという機械規則で反応を落とさない。

### 後から映る人物

全cutの素材poolに顔・衣装等を保持し、実行方式に応じて、対応するentity参照、終了画像への結合、またはshot分割先の開始画像へ割り当てる。終了画像を渡しても途中の登場時刻や顔の完全一致が保証されるわけではない。途中だけ映る人物は終了画像のみでは表現できない場合もある。能力不足は該当shotで具体的に示し、参照を黙って落としたり初手から全員を描かせて解決しない。

画像ペアがある場合は作者が実画像を見て、衣装の一部・付着物・個体数・位置関係・光と意図した変更を照合する。構造validatorはIDs/hashes/割当てを検証し、画素の自然さを判定したと偽らない。毎shotの終了画像生成や独立criticを義務化しない。

## 8. モデル固有の制約

provider/model/input modeを一組で解決し、公式schemaと実adapterの対応を記録する。Higgsfield Kling 3.0 Standardのimage URL、last URL、3–15秒等の確認事項はresearch.mdを参照。

現在のhiggsfield capability分岐はSeedance向けであり、会話で使用しているKlingを共通経路へつなぐ作業が別途必要。`elements`の仕様は未確認なので任意素材URLの転送として実装しない。未検証の入力組合せは検証済みに見せない。

「指示2個」「主動作1つ」は確認した公式APIの数値制限ではない。採用した生成方式に応じた制作方針として扱い、文字列を黙って切り捨てない。必要なカメラ操作が多ければ作者へ具体的な競合/長さの問題を返すか、許容されたshot分割を選ぶ。送信JSONと表示previewは同じ固定snapshotから作る。

## 9. 人が確認する場所

scene内のcutを横に並べ、意図・注視点・画角・見える人物/部位・動き・参照・音声尺を一緒に読む画面を提案する。未生成なら構図メモ、生成後は実画像を表示し、図解を実生成画像と混同しない。

**赤ペンQ2**: この一覧を先に作るか、当初は既存の個別previewを使って共通バックエンドを先に実装するかを選ぶ。新画面ではカードを開くと最初/途中/最後の見せ方と実参照を確認でき、自然文で「顔を出さず背中で」「この人は途中から」を訂正できる。通常は自動で進められ、毎cutの承認操作を必須にしない。

自動採点や画角バリエーション不足の足止めは置かない。参照不足・unsupported mode・欠落した必須入力のみ生成前に止める。失敗出力の破棄と有料再生成は、既存の生成操作/予算範囲に従い、レビュー画面を作っただけで新しい再生成権限を得ない。

## 10. 互換性と移行

古いversionは意味を保って読み出す。新契約を持たない既存cutを、全員表示を正解とする新データへ自動変換しない。author policyとschema versionを更新し、再設計の影響範囲を見せる。承認済み画像/動画/音声は保持する。

**赤ペンQ3**: 新規制作とユーザーが選んだcutだけ新方式を使う案を推奨する。代案は既存作品の未生成cutをまとめて再設計すること。どちらも既存採用ナレーションと生成済みメディアは自動再生成しない。再設計で必要参照が変わった画像はstaleとして理由を表示し、依存先を曖昧なまま使わない。

## 11. 実装範囲と受け入れ

tasks.mdの順で契約→投影→adapter→共通入口→UI/skillsへつなぐ。各段階で同じ意図・IDが残ることをテストする。まず費用のかからないfixtureとrequest previewで確認し、有料生成による画の確認は別に対象を決める。JSON契約だけで映像の芸術的品質やモデルの演技遵守を保証するものではない。
