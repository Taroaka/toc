# 作者の意図と時間別の可視性を分ける設計案

状態: 提案。現在のruntimeが受け付けるschemaではない。既存runや生成コードは変更していない。

## 調査した問題

`toc/p400_authoring.py` の `SCENE_FORMAT.character_ids` は、開始画像に見える人物を意味する。
しかし `toc/p400_projection.py` はその同じ配列を、画像の人物・参照だけでなく
`viewer_contract.required_roles`、`continuity_contract.character_ids`、
`asset_dependency.character_ids_required`にも投影する。
`visible_state_keys`は状態の文章を選ぶ機能で、人物配列や参照の時間別選択にはなっていない。

全参加者を開始画へ出すvalidatorがあるわけではない。文章では世界の状態と可視範囲を
区別するよう指示されている。ただし、途中から見せる人物も素材として保持しようとすると、
一つの人物配列に入れた結果、開始画の被写体・参照にまで入る構造がある。

`allowed_new_reveal_elements`で途中の出現を文章として許す経路は既にある。
しかしそれだけでは人物ID・その人物の衣装状態・実際の参照画像を一組として束縛できない。
設計文章を増やすだけではこのデータ上の兼用は解消しない。

## 判断を先にし、JSONには選んだ実行内容を残す

先に作者が「何をしたいか、何を届けたいか」を考える。その意図に合う視点・見せる順序・
演技を選び、その結果を実行用JSONへ落とす。思考過程全体を固定項目で提出させない。
意図や採用理由は自然文で持てるようにし、構成・感情名・beat数を選択式の固定梯子にしない。

構造化するのは、実行を誤ると困る人物/素材の同一性、状態、可視範囲、参照、接続、尺など。
JSONの妥当性は作者の表現意図の良し悪しを採点するものではない。

## 分離したい概念

| 概念 | 責務 |
| --- | --- |
| 場面全体の参加者・素材 | 途中で必要になる人物も登録し、顔・衣装・道具を失わず保持する |
| 世界の状態 | 人物がどこにいるか。画面外にいることは世界から消えたことではない |
| 開始時に見せる範囲 | 最初の画像に描く人物・物、画面外に置くもの、注目先 |
| 途中の見せ方 | 視線・カメラ・実際の入場等、何を契機に何が見える/注目されるか |
| 終了時の状態と可視範囲 | 到達時点の人物・衣装・道具・反応と、それを見せる範囲 |
| 実際の生成入力 | フレームごとの画像参照と、動画へ送る開始/終了画像または対応した参照入力 |

「全員を最初から見せる」は正当な選択の一つとして残す。既に対話中の場面などで無理な登場を
追加しない。全員が映っていても焦点や視線で発見を表せる場合がある。
既知の人物でも、その場にいることが未提示なら観客にとっての発見は成立する。

## データ形の例

以下は役割を説明するための草案。名前・型・versionは実装前に既存契約と統合して確定する。
`intent`も新しい必須回答欄の提案ではなく、既存のpurpose/direction等で表現できる。

```json
{
  "intent": "主人公が相手に気づき、自分から働きかける選択を見せたい",
  "participant_ids": ["person_a", "person_b", "person_c"],
  "initial_view": {
    "visible_character_ids": ["person_a"],
    "offscreen_character_ids": ["person_b", "person_c"],
    "attention": "person_aが手元の物を見る"
  },
  "visibility_changes": [
    {
      "character_ids": ["person_b", "person_c"],
      "presentation": "camera_reveal",
      "trigger": "person_aが二人に気づいて視線を向ける",
      "world_presence_change": false
    }
  ],
  "end_view": {
    "visible_character_ids": ["person_a", "person_b", "person_c"],
    "state": "働きかけへの反応が読み取れる"
  }
}
```

カメラが見せる、人物が歩いて画面に入る、注目だけが移る、物語世界で新しく生まれる、を
同じ「出現」にまとめない。画面外から見えるだけの人物に、新しい遭遇や移動の事実を捏造しない。
見せる順序は自由に設計し、秒数指定は必要な場合だけ持たせる。

## 下流への投影

1. 参加者全員の素材はcutの資源として保持する。開始画のvisible一覧へ自動展開しない。
2. 開始画像のpositiveな描画対象と参照は、その時点の可視範囲へ絞る。
   画面外人物の素材を用意したことを、その人物を開始画へ描く指示に変換しない。
3. 終了画像はその時点の可視対象・衣装状態の素材を使う。開始画像を空間の手がかりにしつつ、
   意図したカメラ移動や構図変更は許す。服装等の不意の変更と、正当な見え方の差を区別する。
4. 動画には途中で見せる人物のID・外観と、sourceに沿った登場/注目の契機を束縛する。
   `allowed_new_reveal_elements`は新しいtypedな参照との対応を保ち、ただの人物名で済ませない。
5. providerが受け取れる開始/終了画像または参照modeへ変換する。途中から見せる人物の
   外観を実入力へ渡せない場合は、対応mode・終了画像・cutの分け方を解決し、黙って参照を落とさない。
   参照の都合だけで全員を開始画へ詰め込まない。

## 人物ごとの目的から演技へつなぐ

追加要望: 登場人物を決めた段階の感情・意図を、動画の具体的な動きへつなげたい。
ここでも作品や動画を生成せず、共通の設計案として整理する。

「悲しい」「不満」だけでは動作は一意に決まらない。「こちらを向いてほしい」は、
感情名というより相手に求める反応・目的である。同じ感情でも、近づく、避ける、黙るなど
異なる行動があり得る。作者が関係・立場・状況から行動を選び、感情から身振りを固定変換しない。

現行の `execution.performance` にはcut単位の `action / observable_reaction / timing` があり、
`execution.staging.action_sequence`で人物ごとの行為を文章として書ける。
`cast_context`には人物の演技の一貫性資料を渡せる。動画への投影経路は既にあるが、
そのcutで誰が誰に何を求めるかを、独立した人物別の束縛として持つ形ではない。
人物の恒常的な性格、cutの観客向けaffect、その瞬間の各人物の目的も混同しない。

改善案では、重要な演技を担う人物について必要な分だけ、次を結び付ける。

- 安定したcharacter/member参照と、働きかける相手の参照。
- その瞬間の感情・目的と、その根拠（原作事実、ユーザーの演出指示、作者の解釈を区別）。
- 作者が選んだ観察可能な行為、契機、視線/手/姿勢/距離、相手の反応を受けた次の行為。
- 維持する外観/衣装/持ち物と、動かすことを選んだ身体部位や位置の区別。

全人物に必須の心理質問票を作らず、静止・無反応・画面外を選んだ人物を無理に動かさない。
二人が同じ目的を持っていても同じ身振りを同時に繰り返させず、役割やタイミングを選ぶ。
例えば一人が手振りで注意を引き、もう一人が少し身を寄せて視線を求め、相手が向いたら
身振りを弱める、といった関係のある行動へできる。これは選択肢であり定型ではない。

説明用の草案（現行schemaではない）:

```json
{
  "performances": [
    {
      "actor_id": "person_b",
      "target_id": "person_a",
      "objective": "こちらに注意を向けてほしい",
      "emotional_context": "期待と少しの焦り",
      "intent_basis": "user_direction",
      "chosen_behavior": "相手の視線を追い、手のひらを見せる小さな身振りで話しかける",
      "response_when_noticed": "相手がこちらを見たら身振りを弱め、視線を合わせて説明を続ける",
      "preserve": ["衣装と装飾の付着", "持っている物の数"]
    }
  ]
}
```

この判断は人物別で保持し、画像と動画には異なる範囲を渡す。画像にはその時点で見える人物の
姿勢・視線・表情だけを描かせる。動画には、誰が何を契機に動き、相手がどう返し、どう終えるかを
順序付きの具体的な演技として渡す。画面外の人物の演技計画を、開始画への登場指示にしない。
必要なら目的や感情を短い演技文脈として添えるが、内部IDや設計全文をprovider proseへ流さない。
人物の目的を原作にある台詞と扱ったり、そのままTTSへ送ったりしない。

「衣装を変えない」は「人物を動かさない」ではない。不自然な形状変化を防ぐ指定と、
意図した手振り・移動を同時に成立させる。安全側の既定文として全人物を呼吸・瞬きだけに
制限すると、作者が選んだ演技を失うため、実送信promptで矛盾がないか照合する。

## 構造検証の境界

検証するのは登録IDとの対応、フレームごとの可視対象と参照の対応、計画された可視性変化、
衣装状態の適用範囲、source/revealとの整合、実ファイル/hashとproviderの対応能力。
「全員が開始時点で映っているか」「起承転結がそろうか」「感動するか」は合否条件にしない。
意図した見せ方を考えるのはauthor。出力の意味や演技を、JSONが通っただけで確認済みとしない。

## 段階的な実装案

- まずfirst-frame可視人物とcut全体のparticipant/asset依存を分ける。既存 `character_ids` の
  意味を黙って変えず、旧runの読込みと再開を保つversion/移行方針を決める。
- 次に途中の登場/カメラによる提示を人物・衣装の参照へ束縛し、p600/p800で同じ契約を使う。
- 同じparticipant/member参照へcut固有の目的・選択した演技・相手との応答を結び、既存の
  performance/staging投影を人物別に保持できる形へ拡張する。恒常的なcast設定とは分離する。
- 最後にフロントと会話の両経路で、隠す対象が開始画像へ混入しないこと、終了/動画入力では
  必要な参照を失わないこと、人物別の演技が別人へ付かないこと、画面外人物を開始画へ
  押し戻さないこと、全員可視の正当なケースや旧runも壊れないことを回帰検証する。

これは設計案であり、このJSON例が既存の生成処理で使用可能になったという報告ではない。
