# SEO Rank Watch

対象サイトの Google 検索順位を継続的に改善する。目的は、1位を取れそうなキーワードを見つけ、検索ニーズに答える改善を1つ行い、7日間観察すること。このサイクルを実行ごとに繰り返し、1位になったキーワードは監視だけに切り替える。

## データ

以下は対象サイトのリポジトリを基準とする。既存データがある場合はその形式を確認して維持する。初回は候補の根拠を確認して作成し、順位を推測して埋めない。

| ファイル | 内容 |
| --- | --- |
| `data/seo/watchwords.json` | キーワード、対象ページ、優先度 |
| `data/seo/rank-history.json` | 順位履歴。過去レコードは変更せず、新しい測定だけを追記 |
| `data/seo/improvement-log.json` | 改善履歴、status、次回レビュー日、実測の判定結果 |

新規作成時は各ファイルを JSON 配列とする。キーワードと対象ページの組を識別単位にする。

- watchwords の項目: `keyword`, `targetPath`, `priority`（`high` / `medium` / `low`）。対象ページは公開 URL に解決できるパスとする。
- rank-history の項目: `measuredAt`, `keyword`, `targetPath`, `source`（`gsc` / `websearch`）, `startDate`, `endDate`, `rank`, `impressions`, `clicks`。WebSearch で不明な数値は `null` とし、0を捏造しない。
- improvement-log の項目: `keyword`, `targetPath`, `status`, `nextReviewDate`, `actions`, `reviews`。改善・レビューの過去記録を残す。

| status | 意味 |
| --- | --- |
| `active` | 改善候補 |
| `observing` | 改善後7日間の観察中 |
| `achieved` | 1位達成。監視のみ |

日付は対象サイトの運用タイムゾーンで `YYYY-MM-DD`、測定時刻はタイムゾーン付きで記録する。GSC の集計日付・検索種別・国・デバイス等の条件も記録し、比較する期間で揃える。

## 1. 順位を測る

原則として Google Search Console（GSC）を使い、キーワードと対象ページに対応する平均順位、表示回数（impressions）、クリック数（clicks）を取得する。前回からの順位変動は、測定元・対象ページ・集計日数・条件が同じ履歴で比較する。

対象環境に次のヘルパーが導入済みであれば使用する。

```bash
node .claude/skills/seo-rank-watch/scripts/fetch_gsc_ranks.mjs \
  --repo <REPO_PATH> --append
```

このコマンドは対象環境にヘルパーが存在する場合の呼び出し例であり、ToC の本スキルには取得スクリプトを同梱していない。実行前に存在と設定を確認する。未導入なら、利用可能な GSC 連携ツールまたは既存の GSC 取得処理で同じデータを取得し、履歴へ追記する。認証情報の不足を順位データの欠損や0表示と取り違えない。

GSC が使えない場合、または当日の順位を補助的に確認する場合のみ WebSearch（利用環境の Web 検索ツール）を使う。検索結果上の順位は概算であり、GSC を正とする。検索結果から順位を確認できなければ不明とする。WebSearch の記録は GSC の平均順位と混ぜず、検索日時・条件・根拠 URL を残す。

`rank: null` かつ `impressions: 0` は未インデックスとは限らない。必要なら WebSearch で掲載状況を補助確認し、見つからないことだけで未インデックスと断定しない。

## 2. 7日経過した改善をレビューする

`observing` かつ `nextReviewDate <= 今日` の項目を確認する。効果判定には28日平均ではなく7日 GSC を使う。

```bash
node .claude/skills/seo-rank-watch/scripts/fetch_gsc_ranks.mjs \
  --repo <REPO_PATH> --days 7
```

ヘルパーがない場合は同じ7日分を GSC 連携ツール等から取得する。取得可能な確定済みデータの範囲を確認し、改善前と改善後の同じ条件・各7日間を比較する。改善前の7日基準値と集計期間は改善時に保存しておく。28日平均の `rankAtAction` と改善後7日平均を直接比較しない。

- 1位 → `achieved`。GSC の7日平均順位が1.0であることを根拠にし、丸めて1位にしない。
- 改善したが1位未達 → `active`。
- 効果なし・悪化 → `active`。次回は前回と違う改善方法を使う。
- GSC が取得できない、改善後7日分が揃わない、比較できる表示実績がない → 判定保留。`observing` を維持し、理由と次のデータ確認日を記録する。WebSearch だけで効果判定や `achieved` への変更をしない。

平均順位の数値が下がれば順位は改善しているが、変更の因果効果を断定しない。`reviews` にレビュー日、比較期間、前後の順位・表示回数・クリック数、判定理由、判定後の status を記録する。`achieved` の順位が落ちた場合もこの運用では監視・報告のみとし、勝手に改善対象へ戻さない。

## 3. 今日改善するキーワードを1つ選ぶ

`observing` と `achieved` は除外する。以下の順で1キーワードだけ選ぶ。

1. 2〜10位かつ impressions あり。1位に近いものを優先。
2. 11〜20位かつ impressions が多いもの。
3. レビューで「改善したが1位未達」または「効果なし」となったもの。
4. 高優先度の `rank: null`。
5. GSC で見つかった有望な未登録クエリ。対象ページと検索ニーズを確かめ、採用する場合に watchwords へ登録する。

平均順位は小数のまま扱う。1位未達の1〜2位の間も「1位に近い」候補として最優先群に含める。同順位なら impressions、優先度を判断材料にする。候補がなければ順位チェックと報告だけで終了し、無理に対象を作らない。

## 4. 検索ニーズを分析する

改善前に必ず次を行う。

1. 「誰が・何を知りたくて検索しているか」を1〜2文で定義する。
2. WebSearch で現在の上位1〜3ページを確認する。これは検索意図・競合内容の調査であり、順位の正本を置き換えるものではない。
3. 上位ページと対象ページを比較し、検索ニーズに対して不足する情報を特定する。参照 URL と調査日を残す。

SEO のために文章量を増やさず、検索ユーザーが欲しい情報を追加する。上位ページや対象ページを確認できずギャップを特定できない場合、憶測で変更せず制約を報告する。

## 5. 1つのキーワードを改善する

ギャップに応じて、必要な改善だけを実装する。

- title / description / 導入文 / FAQ の改善
- 不足コンテンツの追加
- 記事 ↔ 地域ページ ↔ 詳細ページの内部リンク
- 根拠を確認できた実データの追加

内部リンクは検索ユーザーの「次に知りたい・やりたいこと」へ誘導する。1回の実行で改善するキーワードは必ず1つだけ。共通部品や同じページの変更が観察中の施策に干渉するなら、別候補を選ぶか見送る。

`noindex` の変更や大きなページ構造変更は提案し、承認を得てから適用する。対象サイトの検証・公開手順と、既に与えられた公開権限の範囲に従う。

## 6. 改善を記録して7日待つ

improvement-log に実際に行った改善を追記する。以下の日付・順位は形式例であり、実測値に置き換える。

```json
{
  "keyword": "...",
  "targetPath": "...",
  "status": "observing",
  "nextReviewDate": "2026-09-16",
  "actions": [{
    "date": "2026-09-09",
    "rankAtAction": 4.2,
    "needs": "検索ニーズ",
    "done": "実際に行った改善"
  }],
  "reviews": []
}
```

actions には測定元、改善前7日の基準値と期間、変更ファイル、公開反映日時も保存する。観察開始は検索ユーザーに変更が反映された日で、`nextReviewDate` はその日+7日とする。公開待ちのローカル変更は公開待ちと明記して保持し、反映前に観察日数を消化しない。公開待ちの変更があるキーワードへ重複実装しない。

`observing` のキーワードは `nextReviewDate` まで絶対に再改善しない。期限が来てもレビューで `active` になるまでは改善しない。

`data/seo/*.json` の今回の変更は Git にコミットする。差分を確認し、順位履歴の過去レコードが変更されていないことを確認する。今回のファイルだけを明示してステージし、無関係な作業や秘密情報を含めない。コミットできない場合は未完了として理由を報告する。

## Report

最後に簡潔に報告する。

- 前回から大きく上昇 / 下降したキーワードと実測差分・比較期間
- 今回行った効果判定（保留は理由も記載）
- 今日選んだキーワードと選定理由（なければ対象なし）
- 推測した検索ニーズ
- 実際に行った改善と公開反映の状況
- observing 中のキーワードと nextReviewDate

順位改善を予測で断定しない。変更した内容を報告し、効果は次回の実測で判断する。

## Guardrails

- Google SERP を独自スクリプトでスクレイピングしない。GSC または WebSearch を使う。
- 1回につき改善は1キーワードだけ。
- observing の7日間クールダウンを厳守する。
- rank-history.json の過去データを書き換えない。
- 認証キーや秘密情報を出力・コミットしない。
- noindex や大きな構造変更は承認なしで適用しない。
- 改善効果を断定しない。
- 改善対象がなければページを変更しない。

「測定 → 1位に近いワードを1つ選ぶ → 検索意図を調べる → 改善 → 7日観察 → 実測で判定」を繰り返す。
