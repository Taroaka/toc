# 広告の仕事をAIへ渡す判断

ここでの手順と例は、ToC・EC向けの独自の運用設計。教材の参照先は [対応索引](../coverage.md)。既成プロンプトの再現ではなく、依頼の状況に応じて作業を組み立てるために使う。

## input

「広告を作る」を、対象・相手・行動・根拠・素材・制約へ具体化する。役割名だけを足しても、商品について知らない情報は増えない。「ECの広告担当」と指定するより、商品の事実、購入前に迷う点、掲載面、出力形式を渡す方を優先する。

音声や箇条書きの依頼は、原文にある希望を残したままブリーフへ整理する。事実を補完するための推測と、構成を整えるための編集を分ける。仮の顧客像は仮説と記し、購入者の発言にはしない。

必要情報が足りないときの判断:

| 状況 | 進め方 |
| --- | --- |
| 商品ページやrunが指定済み | 先に読み、分かることを聞き直さない |
| 掲載先は未定、企画だけ頼まれた | 形式に依存しない訴求案を作り、掲載面は未定と記録 |
| 商品・作品を特定できない | 対象のURL・パス・名前を確認する |
| 売上実績がない | 使用場面や確認済みの特徴で案を作る |
| 生成費用や配信費用の許可がない | 原稿・設計は進め、費用が発生する実行の前に範囲を確定 |

## process

一つの成果物に違う種類の判断が混ざるほど、途中の間違いが下流へ広がる。商品事実の抽出、仮説づくり、広告文、映像指示を分け、確定した前段の情報を後段の入力にする。毎段階のユーザー承認を要求する意味ではない。日常の整理や修正は継続し、本人しか決められない目的や重大な条件だけを確認する。

曖昧な依頼では、最初に選択肢を広げる。作る案が定まったら、コピー・文字数・素材・出力サイズを厳密にする。アイデア段階から色や配置を細かく固定して、良い別案を潰さない。

## output

必要な結果に合う形を指定する。比較したいなら同じ列の表、編集へ渡すなら時間付き台本、生成へ渡すなら参照ファイル付き仕様にする。大量の説明文を返して再入力を必要にする状態を避ける。

各成果物には「どの案か」「何を使ったか」「どこが未確定か」を残す。文字数や合計尺のように計算できることは計算し、モデルの自己申告だけを証拠にしない。

## references

参考広告から転用するのは、情報の順序、見せる役割、比較する考え方。コピー、固有の映像、ブランドの表現をそのまま置き換える作業にしない。実績が確認できる自社広告なら、対象・期間・配信面・費用も併せて読む。競合広告は、成果が不明なら「参考」として扱う。

似た例ばかりを集めると同じ案に寄る。用途に合えば、商品単体、利用場面、説明図など異なる見せ方も比較する。例の形を使う場合でも、主張は今回の商品の根拠へ置き換える。

## revision

修正指示は「もっと良く」ではなく、観測した欠点と保持する部分を示す。

- コピーの重複: 同じ価値を言い換えただけか、異なる役割があるかを確認する。
- 主張の不足: 根拠を足すか、言える範囲へ弱める。数値を作らない。
- 表示の問題: 文字崩れ、読めない注記、商品変形など、実物の箇所を特定する。
- 比較版のずれ: 本来固定する背景・尺・音などが変わっていたら揃える。

変更の必要がない箇所まで書き直さない。修正で目的がぼやけた場合は、原稿を磨き続ける前にブリーフへ戻る。仮説を評価した点数は、市場で効くことの証明ではない。

## memory

案件ごとに入力、採用案、生成・編集結果、費用、反応、変更理由を保存する。次のチャットでは「最新の確定版」と「次の問い」を先に読む。案件固有の事実を一般スキルへ混ぜない。

学習を増やす材料は、商品を使った観察、購入・未購入の理由、問い合わせ、配信結果。制作者の好みだけで勝ちパターンを決めない。日々の全ログをスキルへ追加するのではなく、複数の案件で再利用でき、適用条件を説明できる判断を残す。
