# 会話からのメディア生成：進捗と実入力の照合

動画・画像・ナレーション音源・BGM・SEを会話から生成するときの共通手順。
生成を担当するエージェント自身が、今の物語と実リクエストを照合する。
別の採点工程、承認証明、固定の演出規則を追加するものではない。

## 対象と進行状況を復元する

1. ユーザーが指定したToCプロジェクトとrun、scene/cutまたはcueを特定する。
   ファイルの更新時刻だけで作品や採用版を選ばない。「全cut」は会話上の対象sceneか
   全編かを区別する。解決できない対象だけを質問し、独立した確認は進める。
2. `p000_index.md`、`state.current.json`、`run_status.json`を入口にする。
   表示が食い違う場合は`state.txt`の該当履歴と、実際のmanifest/candidate/ファイルを照合する。
   完了フラグだけでファイルや参照が存在すると見なさない。
3. 今回の範囲に関係する`story.md`、`script.md`、`video_manifest.md`、
   `cinematic_direction.json`、採用情報、human change request、生成journalを読む。
   対象cutだけでなく直前・直後の状態と、離れた場面から再利用する素材の由来を確認する。
   音響はscene/全編の意図と実タイムラインも読む。
4. 会話中の最新指示を保存済み設計と突き合わせる。未反映の演出・採用指示は、
   対象を特定して設計/requestへ反映してから生成する。別スレッドの変更は現物を読み直す。
   修正内容が不明な場合は必要な部分だけ確認する。
5. 各対象を「再利用」「新規/修正生成」「実行中の続き」「入力不足」に分類する。
   採用済み・有効な素材を、対象に含まれているだけで再生成しない。

### Cut内のショット設計を修正する

manifest cut内を複数shotへ分ける修正では、[Cut内ショット設計](shot-direction.md)を読み、ユーザーの意図から対象cutの `shot_plan` だけを更新する。shot列は親cutの視覚timelineを使い、source/story/script、rootworldやasset registry、他cut、親cutの音声・語り・cut contractを変更しない。設計の保存・request再materializeは画像/動画の生成実行ではない。既存候補のbytesは保持し、古くなったvisual request bindingだけを無効化する。画像・動画を生成するときは通常の画像/動画stage readsetと生成依頼の範囲に従う。

## 物語上の状態と参照を確認する

- この時点で存在する人物・物、人数/個体数、衣装、靴、手に持つ物、位置関係、
  移動方向、時間帯、まだ開示しない出来事を確認する。作品ごとの値をスキルへ固定しない。
- 「変わるもの」は元の状態と結果の状態を分ける。魔法だけでなく、衣装・外観・材質・
  損傷・構造など、同一性の保持に必要な状態差を対象にする。一時的なポーズとは分ける。
- asset ID → 選択した状態variant → 実ファイル → scene画像の参照 → 動画の参照入力、
  の接続を追う。背景に描かれていること、promptに名前を書くこと、ファイルを保存したことを
  「APIに参照として送った」ことと混同しない。
- 中立の素材シートは、場面の終了画像ではない。必要な終了画像は、開始画像を構図の参照にし、
  変化後の素材も参照して同じcut内の補助画像として生成する。
  `state_variants` / `result_state_reference` / `result_frame`は
  [素材設計](asset-bibles.md)と[画像設計](image-prompting.md)の現行契約に従う。
- 過去runに新しい宣言がない場合も、実際に変化が描かれるかを作者が確認する。
  欄がないことを「参照不要」と解釈しない。必要な設計と素材を対象範囲で補う。
- ユーザーが許可した状態変化と、「何も増やさない」「外見を固定する」などの旧指示が
  衝突していないかを確認する。原稿・設計を直し、コンパイル済みpromptだけで隠さない。

### 個別生成の前に全キャストを比較する

キャラ画像を作成・修正するときは、[全キャストの人物設計](cast-design.md)を読み、
`cinematic_direction.json` の `cast_design` と、最終resourceの人物一覧を確認する。
対象人物だけでなく、役割・関係・顔・髪・体格・衣装・性格/所作の区別を全体で設計する。
集合人物はmemberごとに確認する。全員を違う外見にするのではなく、意図した類似性も保持する。

過去runに全体設計がない場合は、sourceと採用素材から比較を行い、変更候補と保持対象を記録する。
顔や衣装の合格済み素材をこの確認だけで置き換えない。各人物の実promptに外見の設計が届くことを
確認し、性格の説明文を画像へ丸投げしない。動画では役割・所作の基調を読むが、場面の行為を
勝手に変えない。今回の対象外の人物をついでに再生成しない。

### 衣装は人物ごとに引き継ぐ状態

衣装・靴・装身具・髪型は、人物の顔と別に変わり得る視覚状態として扱う。
変化したcutだけでなく、その状態が続く後続cut/sceneも確認する。
主人公だけの確認で終えず、脇役・群の各メンバーを含む画面内の全人物を対象にする。

生成前に、既存のappearance/state variantと採用記録を使い、人物ごとに次を照合する。
必要な記録はrunの既存設計または確認ログに残す。これは新しいruntime schemaではない。

| 記録 | 内容 |
| --- | --- |
| 人物の同一性 | character/memberの識別子と顔・髪の参照。画面の左右を人物IDにしない |
| 現在の衣装状態 | 主要色、シルエット、袖、装飾、靴・装身具など識別に必要な特徴 |
| 適用範囲 | 確認できる開始cut、変化の根拠、次に明示的に変わるまでの引き継ぎ |
| 根拠と実入力 | ユーザー指定・採用済み画像/動画・variantの実パスとhash、今回使う参照 |
| 当該shotの対応 | どの顔がどの衣装を着てどこにいるか。構図変更でも人物との対応を維持 |

- 直前の採用映像に既に衣装変更が反映されているなら、その後の場面でも引き継ぐ。
  場所・カメラ・sceneが変わっただけで初期の人物素材の服装へ戻さない。
  新しい生成物と採用版を区別し、最新のユーザー修正が未反映なら先に設計へ反映する。
- 「姉妹」「同僚」などの集合名の素材が、実際には一人分しか描いていない場合は、
  全員の外観参照として流用しない。人数と各メンバーの対応を実画像で確認し、
  足りない参照を特定する。必要ならメンバー別/状態別素材を用意する。
- 色名だけでなく形・袖・装飾・靴も照合する。人数や顔が合っていても、衣装が同じに
  なったり人物間で入れ替わったりしていれば、その画像を動画入力へ進めない。
  明らかな不一致は必要な画像を修正し、人物の対応を解決できない場合だけ確認する。
- 開始・中間・終了画像と分割生成の継続フレームを、同じ人物別対応で確認する。
  一枚だけを直して旧衣装の参照やpromptを残さない。元の生成物は保持する。
- 衣装を引き継ぐだけのcutに、着替えや変身の演出を追加しない。変更時点が不明なら
  着替えを創作せず、最初に確認できる状態と不明点を記録する。
  衣装が変わらない全cutへ新しいvariantや終了画像を一律に生成する必要はない。

### 開始画像と終了画像の差を実画像で照合する

開始/終了画像の組を使う場合は、promptや同じasset IDだけで一致と判断せず、
生成担当者が両方の実画像を並べて見る。衣装等の細部は拡大して確認する。
画像生成では入力する既存の画像ペアを送信前に確認し、終了画像を新しく作った場合は
生成後に開始画像と比較する。動画生成では、実際に送る最終版の組を送信直前に再確認する。
途中で画像を差し替えた場合と、分割動画の実最終フレームを使う場合も再照合する。

設計から「意図して変わる点」と「維持する点」を分け、既存の確認ログへ短く残す。
前者は姿勢・視線・表情・物の受け渡し・明示された状態変化など、根拠のある差だけとする。
後者は人物の同一性と人数、衣装の色だけでなく襟・袖丈・レースの形/長さ/付着位置・留め具・
装飾・靴、道具の形/数、空間配置、光など、今回変えない要素を含む。
正当な姿勢・遠近・遮蔽・照明による見え方の差を、衣装の変更と機械的に同一視しない。

意図した一続きの動作で到達できない差があれば、該当する画像/設計を直してから渡す。
例えば、袖のレースが別の場所へ付く、布の長さが増える、人物や道具が入れ替わる、といった
差を動画モデルに自然につないでもらおうとしない。画像が各々きれいでも組として確認する。
未解消の差を否定promptだけで隠さず、修正後の実ファイルとhashをrequestへ反映する。
同じ画像を始点・終点に使う方法は、必要な動作と終了状態に合う場合だけ選ぶ。
比較のためだけに、不要な終了画像や全素材の再生成を一律に追加しない。
画像ペアの整合だけで動画途中の形状維持を保証せず、生成後も動作中の衣装・道具を確認する。

### 行為のあとに何が起きるかを設計する

人物間のやり取りが主題なら、物理動作の完了だけでなく、相手の反応と関係の変化まで
そのcutまたは隣接cutで読めるか確認する。受け渡しなら、受け取る、品物を見る、相手へ
視線を戻す、表情やうなずきで返すなど、目的に合う観察可能な反応と必要な時間を設計する。
sourceとユーザーの意図に合わせ、全員を喜ばせる定型にしない。無反応・拒絶・余韻が目的の
場面や無人cutには不要な反応を追加せず、未開示の正体を知った表情等も作らない。
画像は行為前/反応後の各瞬間を描き分け、一枚へ動作列を詰め込まない。
動画は行為から反応へ至る順序を示し、固定ナレーションを変更せず現在の尺内に配分する。
終了画像の表情・視線・手元もその狙いに合わせ、反応のない旧画像へ無理に戻さない。

## 送信直前に実リクエストと比較する

共通の[stage readset](../../workflow/stage-grounding.yaml)と各生成スキルの手順を使う。
固定したrequestについて次を照合し、根拠となる既存snapshot/journalを残す。

| 確認 | 照合する内容 |
| --- | --- |
| 対象 | run、selector/cue、今回の生成理由、採用版との関係 |
| 素材 | source/variant ID、選択candidate、実パス、存在/decode、bytes hash、参照の役割 |
| 尺 | 採用ナレーションの実測・offset・無音・span配置、生成尺と編集上の尺の区別 |
| 設定 | provider、正確なmodel/operation、対応mode、サイズ/比率、音声有無、voice、音響設定など今回に必要な値 |
| payload | 実際の送信prompt/text、参照の配列/first/last欄、解決済みdefault、出力先が設計と一致するか |
| 既存job | request ID、submission状態、未確定の送信、復旧方法、重複課金の回避 |

過去のモデル名・秒数範囲・割引・APIパラメータ名を普遍的な設定として使わない。
現行adapter/ツールschemaを確認し、不明なAPI仕様は公式資料で確かめる。
指定されたモデルを、使いやすい別モデルに黙って置換しない。
必要な参照を受け付けないmodeでは参照を捨てず、対応経路を解決する。

確認結果は既存ログに追加するか、`logs/media_generation/<operation_id>/context.json`へ
対象、読んだsourceのrevision/hash、採用素材、適用した修正、reuse/generate/resume判断、
不足項目、実requestの保存先を記録する。キーや認証ヘッダを記録しない。
これは追跡用メモであり、このファイルの存在自体を新たな実行条件にしない。

明確な生成依頼と既存の権限があれば、確認結果を短く共有して実行する。
参照欠落・契約不一致・解決不能なユーザー意図がある対象は解消してから送る。
全対象をもう一度ユーザーに承認させる定例ゲートにはしない。

## 実行・復旧・引き渡し

- フロントと同じrequest materializer、provider adapter、candidate/journalの経路を優先する。
  UIで固定済みのrequestと別のpromptを会話用に作り直さない。
- adapterが未対応の明示指定APIを使う必要がある場合は、その差を伝える。
  公式schemaと入力の対応を確認し、同じsnapshot/hash/出力検証を保つ。
  既存adapterがそのmodelに対応していると偽らない。
- 送信前にintentを保存し、受理後すぐrequest IDを保存する。IDがあるjobはpoll/downloadを再開。
  送信結果不明のjobは重複POSTしない。状態照会・事業者履歴でも判別できなければ、
  課金重複の可能性を説明して、その再送だけをユーザーに判断してもらう。
- 自動retryは既存runtimeの上限に従う。新しい有料リクエストになる再生成は、
  明示された修正範囲内の必要な対象に絞る。無制限の改善ループにしない。
- 送信直前と結果の登録前にrevision/hashを読み直す。並行変更があれば既存採用を上書きせず、
  その結果をstale候補として保持して対象を再解決する。
- 保存後は通常のfile/decode、尺、比率/音声stream、hashとrequest対応を検証する。
  視聴・画像確認をした場合は、実際に確認できた動作/音と未確認箇所を区別する。
  decode成功を演出成功や発話混入なしの証明にしない。
- 元素材、生成候補、ユーザー採用、配置/mix、最終renderの状態を分ける。
  previewを正式採用や全編完了として記録しない。採用指示があれば
  [正式反映](../orchestration-and-ops.md#codexスレッドで採用された素材の正式反映)に従い、
  run内の正式参照とappend-only stateへ反映する。
- 完成物をrun内に保存し、絶対パスで再生/表示する。変更対象、再利用した素材、実測尺、
  未解消事項を簡潔に報告する。

## スキルの分担

`toc-video-gen`は動画、`toc-image-gen`は素材/場面画像、`toc-narration-gen`は音声生成、
`toc-bgm-gen`は音楽、`toc-se-gen`は効果音を担当する。
`toc-narration`は原稿の執筆、`toc-image-prompt`は画像promptの設計に引き続き使う。
共通手順は作者の文脈確認を支援するもので、フロントの実行時validatorを置き換えない。
